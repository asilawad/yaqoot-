FIX 1 — SystemInfoPage.tsx: stale localStorage reference (post-SQLite migration)
═══════════════════════════════════════════════
File: src/pages/SystemInfoPage.tsx
Problem: `getStorageSize()` still reads `Object.keys(localStorage)` filtering 
`yaqoot_` keys, and the "storagePath" row is hardcoded to the literal string 
`"localStorage (browser)"`. Both are leftover from the pre-migration 
architecture and now show incorrect info (near-zero size, wrong path).

Required changes:
1. Replace `getStorageSize()`: it must become an async function that queries 
   the actual SQLite file size. Use `@tauri-apps/plugin-fs`'s `stat()` on the 
   database file path. Resolve the db file path via `@tauri-apps/api/path` 
   `appConfigDir()` + `"yaqoot.db"` (this matches the path used in 
   src-tauri/src/lib.rs's `execute_sql_transaction`, which joins 
   `app.path().app_config_dir()` with `"yaqoot.db"` — do not invent a 
   different path). If running in the legacy/browser fallback mode (check via 
   the existing `getRepositoryMode()` export from repository.ts — if it 
   returns `'legacy'`), fall back to the old localStorage-based size 
   calculation instead, since that mode genuinely uses localStorage.
2. Replace the hardcoded `"storagePath"` value: show the real resolved 
   SQLite file path when in `'sqlite'` mode, or `"localStorage (browser)"` 
   only when in `'legacy'` mode.
3. Since size/path resolution is now async, convert the `rows` array 
   construction to be built inside a `useEffect` + `useState`, with a loading 
   placeholder (e.g. "...") shown for the size/path values until resolved. 
   Keep all other rows (version, status) exactly as they are now.
4. Do not change the visual layout, styling, or the `t(...)` translation 
   keys already used — only the data source behind the size/path values.
